This skill is the authoritative home and unified entry point for every ADR operation in the project. Consumer skills invoke `/emergent-adr` with a mandatory operation keyword and that operation's named inputs rather than embedding ADR mechanism specs of their own.

This SKILL.md is an **operation dispatcher**, not a spec. Each operation below points at the authoritative spec file or script and does **not** restate its rules — so the spec lives in exactly one place and maintenance touches only that place. When you run an operation, read the referenced spec in full and follow it; the bullets here only route you.

Authoritative spec files in this skill:

- `ADR-FORMAT.md` — ADR file format, `write` contract, three-section body, atomic-decision format, the `description` field, writing conventions, ADR ids, Source Decision Extract rules, and writer self-check evidence handling.
- `ADR-NECESSITY-CONDITIONS.md` — the public companion authority for ADR necessity-condition judgment semantics and the shared strict-evidence and verdict rules. Its consumers are the main agent's ADR necessity self-check and the `check-should-write-adr` reviewer; each loads this one file as the sole source of the condition semantics. `quality-review` is not a consumer — it judges document quality, never whether the target merits an ADR. The file carries no consumer-specific evidence sources, review timing, input/output schemas, sub-agent orchestration, or flow ordering.
- `CHECK-SHOULD-WRITE-ADR-PROMPT.md` — the verbatim reviewer prompt template for `check-should-write-adr`, instantiated mechanically by `scripts/check_should_write_adr.py`.
- `CHECK-ADR-REDUNDANCY-PROMPT.md` — the verbatim reviewer prompt template for `check-adr-redundancy`, instantiated mechanically by `scripts/check_adr_redundancy.py`.
- `CHECK-ADR-REDUNDANCY-HUMAN-REPORT.md` — the deterministic consumer-presentation shape for a validated `check-adr-redundancy` evaluation report; it is not the operation's semantic output and does not author user-facing ruling questions.
- `QUALITY-REVIEW-PROMPTS.md` — ADR quality-review report schema, dispatch parameters, the three named review modes, and how the per-mode reviewer prompt is mechanically assembled.
- `QUALITY-REVIEW-PROMPT-BLOCKS.md` — the single-authority fragments (shared framework, per-gate, and mode-specific rule blocks) the reviewer prompt is assembled from.
- `SCAN-SUPERSESSION-PROMPT.md` — the field-tested verbatim prompt template and dispatch parameters for supersession scanner sub-agents.
- `scripts/` — the mechanical helpers: `context_derivation.py`, `adr_subfolder.py`, `adr_id.py`, `description_index.py`, `atomicity_lint.py`, `live_atomic_decision_corpus.py`, `scan_candidates.py`, `scan_supersession_input.py`, `scan_supersession_packet.py`, `scan_supersession_ledger.py`, `scan_supersession_result.py`, `scan_supersession_delivery.py`, `scan_rewrite_contract.py`, `scan_cycle_contract.py`, `scan_driven_delivery_contract.py`, `quality_review_contract.py`, `review_prompt_assembly.py`, `preflight_authority_bundle.py`, `necessity_conditions_authority.py`, `check_should_write_adr.py`, `check_adr_redundancy.py`, `review_verdict_report.py`, `revise_contract.py`, `produce_contract.py`, `finalize_draft_adrs_contract.py`, `supersession_converter.py`, `status_calculator.py`, `supersession_mark_back.py`, `conflict_disposition.py`.

## Invocation contract

`/emergent-adr` is a **single skill** — its operations are not split into one sub-skill each. You select which operation runs with an **operation keyword: the first token of the args you pass when invoking `/emergent-adr`**.

The keyword is **mandatory and has no semantic fallback**: if the first token is missing or is not one of the eleven keywords below, `/emergent-adr` **lists the valid keywords and stops** — it never guesses the intended operation from context. The eleven valid keywords are:

- `produce`
- `write`
- `revise`
- `quality-review`
- `scan-supersession`
- `promote-draft-to-active`
- `finalize-draft-adrs`
- `extract-active-adr-desc`
- `read-necessity-conditions`
- `check-should-write-adr`
- `check-adr-redundancy`

**Every operation takes a named input schema and returns structured data, never consumer-formatted output.** The consumer renders the returned data with its own output templates and carries any user response. Each operation's named input schema and output contract is given with that operation below and is the format the caller fills in — the caller does not invent its own.

**`bounded_context_path` is required only when the input does not already carry a target ADR path that can derive it.** `scan-supersession` and `promote-draft-to-active` derive the bounded context from `draft_adr_path`. `write`, `quality-review`, and `produce` accept `target_adr_path` when modifying or reviewing an existing ADR; they accept or require `bounded_context_path` when creating a new draft or when no target path is available.

**Boundary the return contract does not move:** the structured-return rule governs only how data enters and leaves `/emergent-adr`. It deliberately does **not** relocate the supersession lifecycle. A consumer follows this skill's lifecycle operations; it does not re-implement or unbundle those steps.

## Operations

### `produce` — end-to-end draft ADR delivery

Create or modify a draft ADR through the full delivery flow. `produce` controls process and machine handoff: it calls `write` to create or modify the draft, then drives scan-owning delivery around scan-free `revise` — draft-creation supersession scanning (pre-acceptance evidence closure, post-acceptance tail, scan-rewrite write→rescan, and the named `tail_evidence_rereview_budget_exhausted` terminal) lives here, not in `revise`. Its orchestration contract lives in `scripts/produce_contract.py`; the revise↔scan handshake it drives lives in `scripts/scan_driven_delivery_contract.py` on top of the shared scan-cycle mechanical layer `scripts/scan_cycle_contract.py`.

`produce` deliberately runs no `check-should-write-adr` gate: it is a human-invoked entry that no agent flow calls on its own, and the invoking user is the ruling authority on whether the ADR should exist — do not add the pre-write necessity gate here.

Flow:

1. Call `write`.
2. If `write` returns `needs_context_ruling`, stop immediately with `final_status: needs_context_ruling`. Do not invent vocabulary, write a draft, dispatch reviewer, or scan.
3. If `write` returns a written draft, drive scan-owning delivery with `quality_review_mode: full_quality_review` on the written draft's path. Every `revise` call in that one `produce` run shares a single seven-round review budget — `rounds_already_consumed` continues across hand-backs and re-entry so the limit cannot silently multiply. `produce` owns the draft-creation supersession scan cycle; `revise` stays scan-free.

`write` is not a dispatch point: the agent executing the operation performs the writing itself, so this skill assigns no dispatch channel and no model/effort tier for writing. Runtime dispatch defaults and the channel rule live in the `revise` section and the dispatch spec files it routes to.

Input:

- Create mode — `bounded_context_path` and source material.
- Modify mode — existing draft `target_adr_path`; verify it is a draft ADR before modification.

Output — thin wrapper report:

- Direct output includes `draft_adr_path`, `structured_report_path`, `final_status`, and `needs_user_ruling`.
- `produce` writes a thin wrapper JSON report to an OS tmp structured run directory every time, including early terminal states. It records this layer's operation status, the delivery/`revise` sub-operation's report path, whether it advanced to the next step, and the final handoff status; it does **not** copy detailed review, scan, or report fields from the delivery report.
- **`final_status` value set (the authority for both `produce` and `revise`):** `final_status` supports `passed`, `needs_context_ruling`, `blocked_after_review_limit`, `needs_user_ruling`, `needs_scan_evidence`, and `failed`. The `needs_user_ruling` boolean indicates caller handoff to the user and is not itself a failure state. `needs_scan_evidence` is produced by scan-free `revise` when it hands control back; scan-owning callers such as `produce` resolve it inside the delivery loop and do not surface it as a `produce` terminal. When a supersession scan is carried pending, `final_status` is `needs_user_ruling`. `revise` takes these definitions by reference and does not restate the value set.

Early terminal state (produced by the `write` step and carried in `produce`'s thin wrapper report, not by `revise`):

- `needs_context_ruling` returns/report `final_status: needs_context_ruling`, `draft_adr_path: null`, `needs_user_ruling: true`, missing concept/term, suggested ruling input, and skipped reviewer and scan steps.

### `write` — write ADR content

Create a new draft ADR or substantively modify an existing draft ADR. Follow **ADR-FORMAT.md** for section roles, atomic-decision rules, Source Decision Extract, writer self-check evidence, terminal states, and output fields. Run `scripts/atomicity_lint.py` over the draft as a cheap structural self-check; it flags suspects only and does not block.

`write` makes no ADR necessity judgment and returns no necessity verdict: whether the candidate may become an ADR is settled before `write`, in the calling orchestration. The authorization boundary — trust-the-caller, no authorization fields, and the scope one authorization covers — lives in **ADR-FORMAT.md**'s `write` operation contract.

- **Input** — `mode` (`create` | `modify`); `bounded_context_path` for create; `target_adr_path` for modifying an existing ADR; source material for the decision source.
- **Output** — `status` (`written` | `needs_context_ruling`), ADR id when one exists, target path when one exists, whether it was created or modified, created/changed atomic decision ids, Source Decision Extract path when created, writer self-check evidence status, and any context-ruling details.

### `revise` — scan-free draft ADR quality revision

Run ADR quality review and writer repairs that do not need supersession-scan evidence; return a structured result. `revise` does **not** execute `scan-supersession`, own a scan-rewrite loop, invalidate-and-rerun scans, or promote. Findings that need supersession-scan evidence are classified here and handed back to the caller as `needs_scan_evidence`. It delegates writing rules to **ADR-FORMAT.md**, reviewer rules to **QUALITY-REVIEW-PROMPTS.md**, and live active decision support data to `scripts/live_atomic_decision_corpus.py`; its acceptance-loop orchestration contract lives in `scripts/revise_contract.py` — the blocking-finding disposition dispatch lives there. Scan freshness, the tail-scan evidence diff, the named `tail_evidence_rereview_budget_exhausted` terminal, and the scan-rewrite loop live in the shared scan-cycle mechanical layer `scripts/scan_cycle_contract.py`, driven by scan-owning callers (`produce` through `scripts/scan_driven_delivery_contract.py`; `finalize-draft-adrs` through its own orchestration). It reuses those operations' existing input, prompt, and output definitions rather than restating them. `revise` never builds a new draft ADR.

Input:

- Required `draft_adr_path`. The live atomic decision corpus is rebuilt fresh each run; a previous run's report is never a reviewer input.
- Required `quality_review_mode`, one of `full_quality_review` or `frozen_glossary_quality_review` — **no default; if missing or unrecognised, `revise` aborts immediately without semantic inference.** These are revise-level concept names; `revise` maps `full_quality_review` to `quality-review`'s `quality_review` mode and `frozen_glossary_quality_review` to its `frozen_glossary_review` mode. The CONTEXT.md glossary approval preflight mode is never usable for `revise`.
- Optional `source_decision_extract_path` and `source_material`.
- Optional `scan_state`: the caller-supplied current non-invalidated completed scan result for this draft's `## Atomic Decisions` (at least `written_supersedes`). When present, repetition findings reclassify under the established-relationship rule below; when omitted, every `scan_evidence` finding is handed back — `revise` never invents a scan state.
- Optional `rounds_already_consumed` (default 0): continue the shared seven-round review budget from this count rather than from zero. `revise` judges exhaustion against its existing limit and reports how many rounds this call consumed.
- If Source Decision Extract or other support data is missing, `revise` does not stop; it marks the report degraded and lets ADR quality review present the evaluable and non-evaluable ranges per the existing support-data rules.

Flow:

1. Draft ADR acceptance check: run `quality-review` in the resolved mode until either a round has no blocking findings, a scan-evidence finding must be handed back, a user ruling is required, failure, or the shared round limit is exhausted. One delivery's review budget is a single seven-round limit shared by **every** ADR quality-review call across revise re-entries — callers pass `rounds_already_consumed` so there is no second review budget. When the limit is exhausted with blocking findings still open, stop and report `blocked_after_review_limit`.
2. Every review round uses the current target ADR, current Source Decision Extract, and current live atomic decision corpus. If the target or support data changes after a pass, rerun review or mark evidence degraded.
3. Blocking-finding disposition: every blocking finding a round reports is first mechanically dispatched to exactly one disposition class — the machine answer to "who resolves this finding, with what means". The dispatch derives from the finding's `gate_id`; the reviewer never assigns or sees disposition classes, and the quality-review report schema and reviewer prompt are unchanged. The dispatch table:
   - `live_active_atomic_decision_repetition_check` → `scan_evidence` (supersession-scan evidence closure — handed back to the caller);
   - `context_glossary_approval_need_check` under `full_quality_review` → `user_ruling`;
   - every other blocking finding → `writer_repair`.
4. Immediate user hand-offs: any `user_ruling` finding ends the acceptance loop at once with a `needs_user_ruling` terminal carrying the ruling request, not counted as a repair round (the full-mode glossary approval semantics, unchanged).
5. Writer repair: `writer_repair` findings are repaired through `write`'s modify mode on the same draft (`revise` does not build a new draft). A single repair write must cover that round's `writer_repair` findings and must not, through the same write, disposition content belonging to other blocking disposition classes — it must not hand-write `supersedes` and must not touch the atomic decisions a `scan_evidence` finding points at. The same write may also address same-round `non_blocking` findings when the hitchhike rule below allows; `non_blocking` is not a blocking disposition class. At most one repair write runs between two review rounds — scan-rewrite writes owned by the caller are not repair writes and are not capped by this. Even a finding the main agent believes is a false positive still gets a recorded disposition; do not resend the same target/support-data combination unchanged and count it as a new round. Non-blocking hitchhike and pass freeze: only when that round actually performs a blocking-driven writer-repair write may that same write also address same-round `non_blocking` findings — allowed, not required — and never open a separate repair or review round solely for `non_blocking`. Rounds without that writer-repair write — including a zero-blocking pass round, and rounds that dispose blocking via user ruling or scan evidence closure without a writer-repair write — must not rewrite the draft for `non_blocking`. From the zero-blocking pass round until this `revise` run reaches a terminal state, that freeze holds. `non_blocking` findings on a zero-blocking pass round are recorded in this run's detailed report only — they create no writer-repair disposition, consume no review round, and do not delay or reopen the acceptance loop. After a passed terminal, any `non_blocking` not hitchhiked on a blocking writer-repair write is ignored: not delivery debt, not a promote or follow-on must-clear list; later work requires a separate writing effort or run, not bound to this passed delivery. These rules are orchestration-spec constraints on the main agent; they do not add a mechanical gate that rejects every draft rewrite after pass. Blocking-finding dispositions and scan-rewrite-driven writes still proceed under existing caller rules. Scan rewrite remains a separate write path for scan-found rewrite needs only and is not a vehicle for previously ignored `non_blocking`.
6. Scan-evidence hand-back: when a round still has `scan_evidence` findings after any same-round writer repair, `revise` returns `needs_scan_evidence` with the locatable findings (and the atomic decisions they point at) and does not scan. The caller that owns scanning runs `scan-supersession` and may re-enter `revise` with updated `scan_state` and `rounds_already_consumed`.
7. Frozen invariant: under `frozen_glossary_quality_review` the glossary is frozen — a repair `write` modify must not trigger `needs_context_ruling` (the frozen glossary forbids adding or changing terms; vocabulary problems are resolved only with an already-approved term or an ordinary-prose rewrite). If it happens anyway, that is a process error reported as a `failed` terminal; `revise` never invents vocabulary or escalates a ruling. Under `full_quality_review` the glossary is not frozen: when a repair `write` modify surfaces `needs_context_ruling`, `revise` hands off as a `needs_user_ruling` terminal carrying that ruling request — the same user-hand-off semantics as a glossary approval finding from review.
8. Semantic degradation from resolving a glossary gap by rewriting under the frozen glossary is recorded, together with the gap, in this run's final report.
9. Reclassification and conflict, when the caller supplies a non-invalidated completed `scan_state` for the current `## Atomic Decisions`: if it established no supersession relationship for the still-live active decision a repetition finding points at, that finding is reclassified `writer_repair` — an accidental restatement has a writer exit instead of a scan/review ping-pong. If it did establish the relationship and review still reports the finding, `revise` returns a `needs_user_ruling` terminal carrying the review/scan conflict — no rescan, no repair: neither mechanism may overrule the other on the user's behalf. Decision-level matching between a repetition finding and the scan-established relationships uses a revise-side identity the orchestrating agent attaches to the finding it received — `repeated_live_decision`, carrying `target_atomic_decision_id`, `active_adr` (the active ADR's filename; a path resolves by its basename against the scan candidate's filename), `active_adr_number` (compatibility field carrying the active ADR id), and `atomic_decision_id`; the reviewer never writes it and the quality-review report schema is unchanged. Without that identity, any established relationship is conservatively treated as covering the finding: the clash goes to the user rather than letting a repair touch content that may legally restate a superseded decision.
10. Quality passed: `revise` ends `passed` when the last quality-review round has no blocking findings. That pass is quality-only — it does not mean supersession scanning is complete or that the draft is ready to promote. Scan-owning callers run the post-acceptance tail (and any owed re-review) themselves.

Runtime dispatch defaults:

- Dispatch channel selection is routed by runtime and delivery class. On Claude Code, standalone attempt-prompt operations use the native sub-agent adapter while quality-review modes and supersession dispatch retain their documented CLI adapters; every other runtime uses its native sub-agent facility. The complete adapter parameters, reviewer tiers, and exit conditions live in **QUALITY-REVIEW-PROMPTS.md**; scanner stage tiers live in **SCAN-SUPERSESSION-PROMPT.md**.
- Every CLI and native sub-agent dispatch is foreground-synchronous. The main agent must wait for and collect the terminal result before it continues; receiving a dispatch handle is not completion. Parallel calls are allowed only behind a join barrier that collects every terminal result before the next ADR lifecycle step.
- `quality-review` reviewer dispatch uses **QUALITY-REVIEW-PROMPTS.md**. Scanner dispatch uses **SCAN-SUPERSESSION-PROMPT.md**. Do not fork their prompt wording or judgement rules per model.

Output and required JSON report fields:

- Direct output includes `draft_adr_path`, `structured_report_path`, `final_status`, `needs_user_ruling`, and `rounds_consumed`.
- `revise` writes a detailed JSON report to an OS tmp structured run directory every time.
- Top-level report fields include `operation`, `final_status`, `draft_adr_path`, `structured_report_path`, `needs_user_ruling`, `ruling_request`, `rounds_consumed`, `scan_evidence_findings`, `quality_review_rounds`, `final_review_state`, `unresolved_blocking_findings`, `refused_findings`, `degradation_notes`, `child_report_paths`, `skipped_steps`, `evidence_status`, and `errors`.
- `final_status` uses the value set **defined in the `produce` section** (referenced, not restated here). The subset `revise` itself produces is `passed`, `needs_scan_evidence`, `needs_user_ruling`, `blocked_after_review_limit`, and `failed`. Write-stage `needs_context_ruling` is a build-stage terminal produced by `produce`'s `write` step, not by `revise`.
- Evidence flags support `clean`, `degraded_writer_self_check_evidence`, and `degraded_reviewer_evidence`.
- Each quality-review round records round number, reviewer close status, verbatim reviewer report path, target ADR path, Source Decision Extract path, live atomic decision corpus path, per-finding blocking-finding dispositions, and whether the reviewed artifact still matches the final artifact.
- Blocking-finding dispositions are recorded per finding with the disposition class (`user_ruling`, `writer_repair`, or `scan_evidence`) and the disposition result — at least `fixed_by_write_modify`, `returned_for_scan_evidence`, and `not_dispositioned_due_to_user_ruling`; reclassified and review/scan-conflict findings carry their marker.
- Refused findings record a disposition reason. Any unresolved blocking finding prevents `final_status: passed`.
- Child reviewer reports, Source Decision Extract, live atomic decision corpus, reviewer-loop evidence, and the revise report stay in OS tmp structured run directories or equivalent non-bounded-context evidence bundles.

### `quality-review` — independent ADR quality review

Review exactly one draft, active, or archived ADR at a time. Use **QUALITY-REVIEW-PROMPTS.md** for the report schema, review modes, status vocabulary, support-data handling, and dispatch parameters; the per-mode reviewer prompt is assembled by `scripts/review_prompt_assembly.py` from the single-authority fragments in **QUALITY-REVIEW-PROMPT-BLOCKS.md**. The reviewer only reports; it never edits files, asks questions, accepts author intent, reads writer self-check evidence, or reads hidden expected answers.

- **Input** — `target_adr_path`; optional `review_mode` (`quality_review` | `context_glossary_approval_preflight` | `frozen_glossary_review`; default `quality_review`); optional Source Decision Extract path; optional live atomic decision corpus path; bounded-context references needed for self-sufficiency and legal reference closure. Narrowing is carried by the mode name — there is no caller-chosen gate set/order parameter. `context_glossary_approval_preflight` runs only `adr_structural_reviewability_check` and `context_glossary_approval_need_check`, then stops. It is not complete ADR quality review and must not report full quality-review pass. `frozen_glossary_review` is the complete review minus the CONTEXT.md glossary approval need check, run with the glossary frozen; it is a narrowed subset (not an early-stop preflight) and may report a pass. No mode judges whether the target merits an ADR: that eligibility ruling belongs to `check-should-write-adr` before the draft is written, and this blind post-write review is forbidden the source conversation such a ruling needs.
- **Output** — always a persisted JSON report file in an OS tmp run directory, returned as its path; there is no inline report form. The report file is generated mechanically from the reviewer's verdict payload by `scripts/review_verdict_report.py`, not hand-written by the reviewer.
- **Caller action by lifecycle** — a defect keeps the same blocking severity whether the target is draft, active, or archived; only the allowed response changes. Repair a draft through the writer. Change active decision substance only through a new draft and supersession, never by editing the active target in place. An archived target is immutable historical state: report the finding, but do not edit it or create retrospective cleanup work, and the caller must not create a new supersession targeting it. An explicitly authorized migration or special rewrite may act only within its stated scope and does not broaden the ordinary quality-review caller contract.

### `scan-supersession` — supersession scanning

When a `draft/` ADR is created or modified, run the foreground supersession workflow for that trigger draft. An agent may not decide on its own that a change is too small or unrelated and skip the scan; a scan is skipped or deferred only where a governing contract declares it. First build the scan input with `scripts/scan_supersession_input.py`: it derives the bounded context from `draft_adr_path`, enumerates every `active/` comparison target, extracts `{filename -> description}` as advisory metadata, and never filters comparison targets by description. Then build Atomic-Decisions-only full packets with `scripts/scan_supersession_packet.py`; keep those full packet paths for ledger validation and result building. Model stages read compact decision JSON through the scanner prompt in **SCAN-SUPERSESSION-PROMPT.md**. Model output is provisional until structurally validated against the matching full packet by `scripts/scan_supersession_ledger.py` and re-reviewed by the main agent. Only after that review may `scripts/scan_supersession_result.py` write reviewed markable relationships into the trigger draft's `supersedes`; the same result helper also produces zero-active and review-pending structured returns.

Key constraints (do not background, do not silence — the user must see the report to retain the withdrawal right):

- **Empty `active/`** — if the derived context has no active ADR file, including the lazy-folder case where `docs/adr/active/` has not been created yet, **skip the scan**: do not dispatch a scanner and return `status=skipped_no_active`, `candidate_count=0`, `scanner_dispatched=false`.
- **Asymmetric defaults** — bias toward recall on topically-related comparison targets (a missed supersession is silent and worst); when unsure between FULL and PARTIAL, mark PARTIAL; flag low-confidence judgements loudly for priority review.
- **Partial supersession may not be marked directly** — if a new decision only changes part of an old atomic decision, the main agent must first revise the new ADR so it fully restates and replaces the old decision, and only then mark the supersession.
- **Description boundary** — `description` may be extracted for diagnostics or future shadow/advisory ordering, but the baseline operation never removes active candidates, changes mappings, or decides supersession from `description`. The `## Atomic Decisions` section is the decision authority.
- **Structured statuses** — return one of `skipped_no_active`, `completed`, `awaiting_rewrite`, or `awaiting_review`. `awaiting_rewrite` and `awaiting_review` are pending outcomes: surface them to the consumer and stop that operation flow before unrelated questions.
- **Write boundary** — `scan-supersession` writes only reviewed draft-side `supersedes` entries. It never writes active/archived `superseded_by`, never recomputes target status, and never archives targets; those stay in `promote-draft-to-active`.

When `produce` drives scan-owning delivery around scan-free `revise`, the ordinary-path scan still runs after the draft ADR acceptance check accepts the draft — the post-acceptance tail. When a blocking finding itself requires durable `supersedes` scan evidence (`revise`'s scan-evidence disposition handed back as `needs_scan_evidence`), the scan is that finding's disposition and runs before acceptance as pre-acceptance evidence closure. After an accepted scan rewrite, the caller calls `write` and then reruns `scan-supersession` before any further quality-review.

Scan-rewrite loop (owned by the scan-driven delivery layer, not by scan-free `revise`): for an accepted scan rewrite request, call `write`, then immediately rerun `scan-supersession` before any further quality-review. If the rerun scan again returns an accepted rewrite request, continue the write-to-scan loop. A pending scan result — `awaiting_review`, or an `awaiting_rewrite` whose rewrite request the main agent did not accept — stops quality-review and returns that structured pending result to the caller. In the scan-rewrite loop, quality-review may run only after the rerun scan has completed and any required rewrite-related durable `supersedes` evidence has been written. If the completed rerun scan finds no `supersedes` metadata to write, the caller must still run quality-review again before accepting the draft. The non-scan write and reviewer-repair paths still run quality-review. Scanner output cannot drive durable `supersedes` writes or promotion metadata unless structural validation has passed and the main agent has reviewed it. If either condition is missing, return a structured pending or review-needed result. Scan-result freshness: any change to `## Atomic Decisions` after a scan invalidates that scan result (content comparison, mechanical hash); a fresh scan is required before accepting the draft. The delivery report records `scan_rewrite_loops`, `scan_invalidated_by_atomic_decisions_change`, `pending_scan_result`, `final_scan_status`, `scanner_output_structural_validation`, and `main_agent_scan_review`.

- **Input** — a single `draft_adr_path` (the trigger draft to scan); its bounded context — and therefore the `active/` comparison set — is derived internally from this path, so this operation does not take `bounded_context_path`.
- **Output** — a structured object with `status`, `draft_adr_path`, derived `bounded_context_path`, `candidate_count`, `scanner_dispatched`, `description_filtering_used=false`, `decision_authority="## Atomic Decisions"`, `findings`, `rewrite_required`, `low_confidence`, `written_supersedes`, `frontmatter_write_status`, `escalations`, and `diagnostics`. `frontmatter_write_status` is the authority for whether this helper wrote draft frontmatter; `written_supersedes` lists non-empty durable relationships and can be empty when stale `supersedes` metadata was cleared.

### `promote-draft-to-active` — promote one draft into active

Promote a single `draft/` ADR through the **whole** draft→active migration in one call: apply its supersession marks to the targets it supersedes, move the draft itself into `active/`, recompute its own `status`, and return a structured result including an after-report.

The three parts of the promotion:

- **(i) Apply marks to the superseded active targets.** From the draft's `supersedes`, derive each target's `superseded_by` by inversion (swap `ours`/`theirs`, swap the `adr` pointer — use `scripts/supersession_converter.py`), but **only after an LLM re-verifies the target's current state** (still in `active/`, the atomic decision not already superseded by someone else). Recompute each touched target's `status` with `scripts/status_calculator.py`; `supersession_mark_back.py` covers the apply/conflict detection. A target whose **every** atomic decision is now superseded (`status` becomes `fully_superseded`) is moved into `archived/`; a **partially** superseded target (`partially_superseded`) stays in `active/`.
- **(ii) Move the promoted draft itself.** Move it from `draft/` into `active/` and **recompute its own `status` with the same `scripts/status_calculator.py` `compute_status`** (no separate status function) — projected from its new folder and which of its decisions are superseded.
- **(iii) Return structured.** Per target, what was applied; the promoted draft's move and new status; and the after-report.

**Conflict handling is best-effort, never blocking (replaces the old "stop and defer to human judgement").** When the re-verify finds a conflict, the mark is dispositioned per type rather than escalated:

- target **already archived**, or its **atomic decision already superseded by another draft** → skip applying, **remove that entry from the promoted draft's own `supersedes`** (the supersession is now moot), and list it in the after-report;
- target **no longer in `active/`** → skip applying, **keep that `supersedes` entry** (a human may later re-point it), and list it in the after-report.

All three conflict types go into the after-report and are flagged needs-human-review; none of them stops the promotion. Removing a moot entry from the *draft's own* `supersedes` while the draft is still in `draft/` is part of this disposition and is distinct from rollback of already-applied marks.

**The promotion is unconditional.** Any conflict on the target side never aborts it — the draft is always moved into `active/` and gets a `status`, independent of how the marks landed. Every skipped or unresolved item surfaces only in the after-report, never by interrupting the promotion.

- **Input** — a single `draft_adr_path` (the draft being promoted). Its bounded context — and therefore the `active/`/`archived/` folders the marks land in — is **derived internally from this path**; this operation does **not** take `bounded_context_path`.
- **Output** — per target, what was applied (`superseded_by` / `status`) and which targets were archived; the promoted draft's new path and new `status`; and the **after-report**: for each skipped or unresolved item, at least the target ADR, the conflict type, the disposition (skip + cleared entry / skip + kept entry), and whether it needs human review.

### `finalize-draft-adrs` — draft ADR finalization orchestration

Finalize one or more existing draft ADRs to a per-draft terminal state (deleted, promoted, or left unresolved for user ruling). Its orchestration contract lives in `scripts/finalize_draft_adrs_contract.py`. It directly orchestrates entry ADR redundancy checking, `write`, scan-free `revise`, `scan-supersession`, and `promote-draft-to-active`; those operations' input, prompt, and output definitions are taken by reference and not restated here. `revise` is called with `quality_review_mode: frozen_glossary_quality_review`.

- **Input** — `draft_adr_paths` (one or more existing draft ADR paths) and `disposition_scope_git_recoverable_and_isolated` (caller-declared bool premise that the disposition scope is Git-recoverable and isolated from unrelated changes; omit/`None` means undeclared). Bounded context for each draft is derived from its path. Single-draft input degenerates to a linear flow; multi-draft scheduling is owned inside the contract.
- **Input validation** — empty `draft_adr_paths`, duplicate draft identity or path, and any path not under `docs/adr/draft/` are operation failures: structured `invalid_input` failure, no batch summary, no lower-operation calls. This layer must reject `active/` (and any non-`draft/`) itself — the redundancy checker accepts active targets. Path-not-found, empty live atomic-decision sets, and draft-shaped paths the lower layer rejects are delegated and land as per-draft `unresolved`.
- **Flow** — for each draft: run entry ADR redundancy checking once (never again on later revise/scan/rewrite). Branch on the ADR-level result without rewriting it: fully redundant → delete the draft when both semantic and recoverable authorization hold; partially redundant → remove fully-redundant atomic decisions and rewrite partially-redundant ones to the named retained portion via `write`, then continue; fully retained → continue; unresolved or check failure → leave the file untouched and stop as `unresolved`. Auto delete/modify require both authorizations (named decisions still present in `## Atomic Decisions`, and the caller premise True); either missing withholds disposition, leaves the file, and stops as `unresolved` — never skip disposition into quality review. Continuing drafts enter scan-free `revise` under the frozen glossary, then acquire same-bounded-context exclusivity, run a fresh supersession scan, and when no non-promotion work remains promote before releasing exclusivity. Within one finalize run, every `revise` call for the same draft shares one review-round budget: this layer passes `rounds_already_consumed`, advances the cumulative from each call's `rounds_consumed`, and does not reset on scan-evidence hand-back, supersession scan, leaving exclusivity, post-rewrite re-entry, or a later finalization attempt. Exhaustion stops that draft as `unresolved` with no fresh-quota recall path; the numeric cap stays with `revise`. Shared budgeting keeps ADR quality and user-perceived speed in bounded balance — further polish rounds do not change runtime code and have declining marginal benefit. Failure isolation is per draft: an unresolved draft releases its exclusivity slot and does not stop same-context or other-context peers (accepting that a later peer's scan may miss conflicts with a still-unresolved draft — continuing is intentional). Unresolved drafts stay in `draft/`; once judged unresolved they receive no further disposition; lawful writes already applied are not rolled back. Terminal states are `promoted`, `deleted`, or `unresolved`.
- **Exclusivity scope** — same-bounded-context exclusivity covers one single finalize-draft-adrs call only. Callers must merge same-context drafts that may run together into that one call; split calls must wait for the earlier call to finish. This operation creates no cross-call persistent lock and no global lock; overlapping independent calls on the same context are outside the exclusivity guarantee.
- **Output** — a per-draft end-to-end report (entry redundancy result and disposition including auto delete/modify actions with evaluation-report path, action, and recovery point; each `revise` result by path reference; shared review-round budget cumulative; scan role/result with this operation's assigned persistence path for scan output; `promote-draft-to-active` report path; embedded `write` results when any; final terminal and, when unresolved, ruling evidence that distinguishes stopped-at-entry from mid-run) plus a batch summary listing only each draft's terminal, `needs_user_ruling`, and end-to-end report path (single-draft still emits a one-row summary; input-validation failures write none; unresolved judgment details stay in the end-to-end report). Direct output is the `batch_summary_path`, `structured_report_path`, `final_status`, and `needs_user_ruling` envelope. Its `final_status` is an order-independent batch aggregate defined by the orchestration contract, never a selected draft row; exact per-draft terminals remain authoritative in the batch summary. Reports persist under the OS-tmp run directory.

### `extract-active-adr-desc` — retrieve the active-ADR description index

Extract the `{filename → description}` index of a bounded context's `active/` folder, built from each ADR's frontmatter `description`. This is mechanical extraction only — it reuses `scripts/description_index.py`, which is fed the `bounded_context_path` and resolves that context's `active/` itself, reads the `description` field, and never opens the body.

Deciding **which** active ADRs are relevant to the current topic, and loading their full text on demand, is **not** part of this operation — that judgement needs conversation context and stays with the consumer's opening discipline.

- **Input** — `bounded_context_path` (its `active/` folder is derived from this).
- **Output** — the structured `{filename → description}` index table.

### `read-necessity-conditions` — load the ADR necessity-conditions authority

Load `ADR-NECESSITY-CONDITIONS.md` — the public companion authority for ADR necessity-condition judgment semantics and shared evidence rules — into the caller's context. Run `scripts/necessity_conditions_authority.py`: it resolves the authority file from this skill's own location, mechanically validates the required structure (shared rules first, then the four fixed judgment sections per condition), and prints the structured return — so a consumer needs neither this skill's install path nor any skill-discovery resolution detail.

This is a pure read. The content is delivered complete and verbatim — never summarized, rewritten, or supplemented. The operation extracts no transcript, creates no run directory, dispatches no sub-agent, and produces no review verdict.

**Fail closed:** a missing authority file, content that cannot be read in full, or invalid required structure fails the operation with the explicit reason and delivers no content. There is no fallback — not a caller-side copy, not model memory, not a reconstruction from condition names; the caller's necessity judgment stays unevaluated until a valid authority read succeeds.

- **Input** — none: the operation keyword itself is the complete input; the schema has no semantic parameters.
- **Output** — structured data carrying `authority_full_text` (the complete verbatim document), `source_path` (the resolved authority file path), and `structure_validation` (the mechanical validation status and the condition names it verified).

### `check-should-write-adr` — rule whether a candidate decision may be written as an ADR

Before a draft ADR is created or modified, an independent reviewer sub-agent rules on conversation evidence whether the candidate decision (or decision delta) may proceed to `write`. Create and modify are one operation distinguished by the candidate's `mode` — never two public keywords. This check is never abbreviated "preflight"; that name stays with the post-write `context_glossary_approval_preflight`.

The reviewer prompt template is **CHECK-SHOULD-WRITE-ADR-PROMPT.md**; the whole mechanical layer — evidence cutoff, run/slot/attempt layout, closed verdict validation with evidence line numbers, report assembly, path-line resolution, and redispatch accounting — is `scripts/check_should_write_adr.py`. The reviewer itself, at the start of its run, loads and validates the necessity-conditions authority and formally loads the complete `emergent-design` skill — the semantic basis of its ADR carrier suitability judgment; the caller never pastes, summarizes, or selects condition or philosophy content for it.

Input (named schema):

- `session_transcript_path` — the current session's transcript file, resolved by the caller.
- `candidates` — one or more entries, each `{mode: "create" | "modify", candidate_description, modify_target_path}` (`modify_target_path` only in modify mode). The description is prose carrying two distinguishable semantic blocks — the decision content to record, and for every necessity condition the candidate-specific facts, causal account, and boundary argument the main agent claims — with no required schema, heading literals, or field order. Its semantic responsibility ends at those two blocks. A caller may perform its own upstream routing, but the ADR carrier suitability judgment inside this review belongs exclusively to the independent reviewer; any main-agent `emergent-design` summary, carrier conclusion, or suitability argument therefore makes the description not reviewable, even when embedded inside one of the two blocks. It must not carry conversation evidence locations; the reviewer locates all evidence itself and judges the description's reviewability semantically (labels and summary-level content are rejected). Create mode never pre-atomizes the prose or supplies decision ids; that writing work belongs to `write`.

Flow:

1. **Extract conversation evidence** — run the `extract-transcript` skill on the explicit `session_transcript_path` with its fixed default category selection. This operation fixes that selection; the caller may never add or remove categories.
2. **Cut and prepare** — `python3 scripts/check_should_write_adr.py prepare-round <round_input.json>` delivers the pre-write ADR conversation evidence extract as a fixed JSONL artifact (the extraction truncated right after its latest `user_prompt` record, so the latest ratified answer is included and the current agent turn is excluded; reviewer evidence line numbers index this delivered file) and lays out the unique OS-tmp run directory, one slot per candidate, and each slot's first attempt with its instantiated reviewer prompt and preassigned verdict and report paths. The main agent supplies only the semantic inputs and never hand-writes a path or pairing datum. When the cutoff boundary cannot be achieved, the operation fails here and no reviewer is dispatched.
3. **Dispatch** — one independent reviewer per candidate; reviewers never share candidates, inputs, or results. Multiple candidates dispatch in parallel behind a join barrier; a single candidate dispatches directly and waits for that one result — no batching wait, no cross-candidate grouping, no aggregation-only steps; an empty round is never dispatched. The dispatch channel and the model/effort tiers are the shared dispatch parameters in **QUALITY-REVIEW-PROMPTS.md** (this operation is inside their scope). Prompt delivery follows the same rule as other dispatch points: a non-LLM channel brings the prompt file content in directly where the runtime supports it; otherwise the main agent sends only the attempt's machine-generated `dispatch_bootstrap` line from the manifest, verbatim — so even the bootstrap's prompt-file path is never hand-written. This operation uses no per-run integrity marker: the unique run directory, per-slot preassigned paths, and exact path comparison carry the delivery validation.
4. **Collect** — resolve each reviewer's final reply mechanically (`resolve-reply` reads the reply from stdin): extract the one `CHECK_SHOULD_WRITE_ADR_REPORT_PATH:` line, require it to equal that attempt's preassigned report path, and validate the report — the resolver revalidates the persisted verdict against the delivered evidence extract and the authority's condition set and requires the report file to equal its mechanical derivation, so a hand-written or tampered report never resolves as a review result; all other reply prose is ignored and is never a contract violation. A `CHECK_SHOULD_WRITE_ADR_AUTHORITY_INPUT_FAILURE:` line means the reviewer could not obtain a valid authority: fix the authority input or stop — a fresh reviewer never repairs it and it never consumes the redispatch budget.
5. **Redispatch on incidental failure** — a reviewer interruption, a reply without a resolvable path line, or an invalid verdict/report leaves the slot without a review result; never synthesize a failure report and never guess a semantic outcome. Redispatch a fresh reviewer over the same fixed inputs via `prepare-attempt` (new attempt directory, prompt, verdict, and report paths — late output from an earlier attempt is ignored, never merged). `redispatch_decision` is the stop authority: the same failure class in two consecutive reviewer attempts stops, and at most three total attempts are spent across distinct incidental failures. A candidate that stops without a valid report stays review-not-completed and is reported as blocked.
6. **Join and return** — only after every slot reaches a validated report or a stop state does the operation aggregate and return.

Output — structured data: per candidate, the final review result (`approved`, `rejected`, or review-not-completed with its stop reason) and its validated report path. The report carries the mechanically derived overall result, the mechanically derived `rejected_at` (the semantic stage that stopped the candidate — exactly `description_reviewability`, `conversation_decision_ratification_evidence_check`, `adr_carrier_suitability`, or `necessity_conditions`, or `null` when every stage passed), and the reviewer's semantic judgments only — description reviewability, the two conversation-ratification evidence judgments, the single overall ADR carrier suitability judgment made after ratification passes and before any necessity condition, and every necessity condition's judgment (each mirrored as judged, or a `not_evaluated` shell when an earlier gate stopped the review), plus an optional free-prose parts analysis — each evaluated judgment with its evidence line numbers into the delivered artifact.

Consumption boundary: only a validated `approved` report authorizes calling `write` for that candidate. On a rejection the main agent never writes anyway and never extracts just the passing parts: it either accepts the rejection (abandon the candidate, or adjust the request input and resubmit the adjusted whole candidate as a **new** review round — changed input is a new review version, not a retry) or presents the specific disagreement to the user and writes only on the user's explicit, scope-named clearance; the original report stays a rejection either way.

### `check-adr-redundancy` — report which live atomic decisions are already carried elsewhere

Judge, for one draft or active ADR, which still-live atomic decisions are already fully or partially carried by eligible non-ADR long-lived carriers, which remain ADR-only knowledge, which contradict current codebase ground truth, and which need a concrete missing fact before the classification can close. The keyword names a report-only check: the operation does not modify, delete, archive, or promote the ADR, does not open a challenger reviewer or frozen authority bundle, and does not integrate promotion. After the report is delivered, this operation ends — it does not prescribe cleanup, deletion, or upgrade actions.

The reviewer prompt template is **CHECK-ADR-REDUNDANCY-PROMPT.md**; the whole mechanical layer — target preflight and live-decision set, run/attempt layout, prompt instantiation, closed verdict validation, ADR-level aggregation, evaluation-report write, path-line resolution, redispatch accounting, and the deterministic post-return human-report renderer — is `scripts/check_adr_redundancy.py`. The reviewer itself, before judging, formally loads the complete `emergent-design` skill as the carrier-judgment authority; the caller never pastes, summarizes, or substitutes that load.

Input (named schema):

- `adr_path` — exactly one draft or active ADR path. Path lists and other batch inputs are rejected. Do not name the field `draft_adr_path`. Archived targets fail as unsupported before redundancy judging begins.

Flow:

1. **Prepare target** — `python3 scripts/check_adr_redundancy.py prepare-target <adr_path>` accepts draft/active, rejects archived and illegal paths, and returns the still-live atomic decision set. An empty live set is an unsupported-target failure with `evaluation_report_path: null`; never dispatch a reviewer and never forge a vacuous ADR-level redundancy verdict.
2. **Prepare run** — write a small JSON input carrying `adr_path` and `live_atomic_decision_ids`, then run `python3 scripts/check_adr_redundancy.py prepare-run <input.json>`. It lays out a unique OS-tmp run directory and the first attempt with the instantiated reviewer prompt and preassigned verdict and evaluation-report paths. The main agent supplies only the semantic inputs and never hand-writes a path or pairing datum.
3. **Dispatch** — one fresh-context reviewer for this single ADR. The dispatch channel and the model/effort tiers are the shared dispatch parameters in **QUALITY-REVIEW-PROMPTS.md** (this operation sets no dispatch policy of its own). Prompt delivery follows the same rule as other dispatch points: a non-LLM channel brings the prompt file content in directly where the runtime supports it; otherwise the main agent sends only the attempt's machine-generated `dispatch_bootstrap` line from the manifest, verbatim. This operation uses no per-run integrity marker and no authority bundle.
4. **Collect** — resolve the reviewer's final reply mechanically (`resolve-reply` reads the reply from stdin): extract the one `CHECK_ADR_REDUNDANCY_REPORT_PATH:` line, require it to equal that attempt's preassigned evaluation-report path, and revalidate that the report equals the mechanical derivation from the persisted verdict. All other reply prose is ignored. A `CHECK_ADR_REDUNDANCY_AUTHORITY_INPUT_FAILURE:` line means the reviewer could not formally load complete `emergent-design`: fix the authority input or stop — it is not `indeterminate`, a fresh reviewer never repairs it, and it never consumes the redispatch budget.
5. **Redispatch on incidental failure** — a reviewer interruption, a reply without a resolvable path line, or an invalid verdict/report leaves the run without an evaluation report; never synthesize a forged evaluation report and never guess a semantic outcome. Redispatch a fresh reviewer over the same fixed inputs via `prepare-attempt`. `redispatch_decision` is the stop authority: the same failure class in two consecutive reviewer attempts stops, and at most three total attempts are spent across distinct incidental failures.
6. **Return** — return only structured data carrying the validated report fields and evaluation-report path. That structured report is the semantic authority; the human report is not an additional operation output.
7. **Consumer presentation and interaction** — after the structured return, the consumer may call `python3 scripts/check_adr_redundancy.py render-human <evaluation_report_path>` to apply **CHECK-ADR-REDUNDANCY-HUMAN-REPORT.md**. This deterministic renderer only copies and groups validated fields; it does not generate the user-facing ruling question. When `needs_user_ruling` is true, it presents each `user_ruling_requests` entry as ruling context, then the main agent writes the concrete question in its own words for the current conversation. The consumer does not run a second semantic review and does not accept, reject, or rewrite any evaluation result.

Output — structured data on success: `evaluation_report_path` plus the validated report fields (`adr_redundancy_evaluation_result`, `needs_user_ruling`, `user_ruling_requests`, and the per-decision results). On failure: an operation failure with its class and reason and `evaluation_report_path: null` — no evaluation enum, no forged `needs_user_ruling`, and no evaluation report file.

## Not in /emergent-adr

**Reference-block generation and path-existence checking stay with the consumer.** They are consumer-document content-production logic, so the consumer assembles related-ADR blocks with its own generator and does not route this through `/emergent-adr`. Likewise, the **relevance judgement** needs the conversation context and stays in the consumer. `/emergent-adr` governs the ADR files and the lifecycle mechanism; CONTEXT.md governance (write authority, term retirement) stays with each consumer.
