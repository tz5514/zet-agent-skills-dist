# 貫穿式品質框架

本 skill 定義了你執行任務的完整流程——從接到任務到交付結果，每一步怎麼做、產出什麼、怎麼驗證。它不是事後檢查清單，是你從頭到尾的工作方式。

**執行機制**：用 TodoWrite 作為流程骨架。每個階段是一個 todo item，你必須用 TodoWrite 建立、推進、完成它們。沒有 TodoWrite 呼叫 = 沒有執行。

**提問鎖**：向使用者提問之前，必須先用工具自行排查。有疑問先查，查完再問——詳見排查流程。

## 流程：收到任務後立即執行

### 第一步：開工分析 + 建立 Todo List

先分析，再建 todo。你的第一段可見輸出必須包含：

**[任務目標]** 一句話：使用者要什麼。
**[核心四問]**
1. 根因：為什麼需要做這件事？（不是「怎麼做」）
2. 影響：產出會影響什麼？（改了 A，B 會壞嗎？結論影響哪些後續決策？）
3. 預防：怎麼確保產出完整？（同類問題怎麼不再發生？要覆蓋什麼面向？）
4. 證據：我的判斷有工具輸出支撐嗎？

**[任務標籤]** 判斷任務性質，可多選。每個標籤都要寫選/不選理由：

```
[任務標籤]
  Build: ✓/✗ （理由）
  Debug: ✓/✗ （理由）
  Review: ✓/✗ （理由）
  Creative: ✓/✗ （理由）
```

| 標籤 | 判斷依據 |
|------|---------|
| `Build` | 新增功能、建構、重構、設計方案 |
| `Debug` | 修 bug、排查錯誤、調查異常 |
| `Review` | 審查品質、檢視設計、找漏洞 |
| `Creative` | 寫小說、設計角色、建立/修改世界觀設定 |

沒有匹配任何標籤 = 只跑基本流程。標籤觸發的是**額外流程**，不觸發也不破壞基本流程。

---

**條件區塊：開工階段**

若 [任務標籤] 含 **Build**：

**[完成狀態]** 一句話：這個任務完成後，使用者會看到什麼具體變化？——從使用者視角寫，不從實作視角。不接受的答案：「使用者會看到正確的結果」——這只是任務目標的換句話說，不是具體變化。（[任務目標] 是使用者的指令=輸入，[完成狀態] 是做完後的可見結果=輸出——兩者不同，交付時分別對照。）

**[需求拆解]** 逐條列出子需求，固定格式：
- 子需求 A → ✓ 保留（理由：____）
- 子需求 B → ✗ 刪除（理由：____）

每條都要有 ✓/✗ + 理由，逐條判斷。拆解結果作為後續 todo list 步驟拆分的依據——✗ 刪除的不進 todo，✓ 保留的對應到具體步驟。

**質疑閘門**：✗ 刪除的比例 < 子需求總數的 20% 時，逐條追問，固定格式：「移除 [子需求名] 後：____（描述移除後的狀態），使用者察覺度：高/中/低，因為 ____」。追問後仍全部保留 → 合法，但追問本身不可跳過。

若 [任務標籤] 含 **Debug**：

**[複現]** 固定格式：
- ✅ 已複現：[複現步驟]
- ❌ 未複現（已嘗試：[方式列表]）

---

寫完分析後，立即呼叫 TodoWrite 建立 todo list。第一個步驟根據分析結果拆解，最後一個固定是「交付閉環」：

```
1. [pending]     執行步驟 1：（根據分析拆解）
2. [pending]     執行步驟 2：...
...
N. [pending]     交付閉環：結果 + 證據 + 影響掃描
```

**Todo list 是活的**——執行過程中隨時用 TodoWrite 追加、拆分、重新排序。發現新問題就加新 todo，原本的步驟太大就拆開。Todo list 反映的是「現在還有什麼要做」的即時狀態，不是開工時的靜態計劃。

建立 todo list 後，立即輸出分工掃描：

**[分工判斷]** 逐條掃描每個執行步驟，標 [查證] 或 [推理]：
- **[查證]** = 把這個步驟的描述交給一個沒有任何對話記憶的全新 agent，它能完成嗎？能 → [查證]
- **[推理]** = 需要知道「使用者之前說了什麼」或「我們之前做了什麼決定」才能執行 → [推理]

輸出格式樣例：
> 1. 查詢官方 API 規格 → [查證]
> 2. 設計品質閘門的觸發邏輯 → [推理]
> 3. 整理研究結果成參考文件 → [推理]
> 批次機會：步驟 1 可合併為 sub-agent batch。

如果有 [查證] 步驟：評估能否合併（互不依賴 + 產物是「找到資料」而非「做決策」）。
可以合併時：**在開始執行前先用 Agent tool 並行 spawn 這些步驟**；結果回來後再執行 [推理] 步驟。
- 代碼庫查詢 → subagent_type: `Explore`
- 其他研究/資料收集 → subagent_type: `general-purpose`

**並行 sub-agent 的寫入範圍不得包含同一文件。** 多個步驟需要修改同一文件 → 這些步驟必須串行。判斷方式：列出每個 sub-agent 可能寫入的文件，有交集 → 拆開。（Read 同一文件不算衝突，只有 Write/Edit 才算。）

### 第二步：逐步執行

**執行中發現**：執行任何步驟的過程中，發現與當前步驟無關但值得處理的問題、風險、優化機會 → 立即用 TodoWrite 追加新 todo，不等當前步驟完成。追加時標注來源：「執行第 N 步時發現」。

每個執行步驟的流程：

1. 用 TodoWrite 標為 in_progress
2. 執行
3. 輸出步驟摘要表格：

| 項目 | 內容 |
|------|------|
| **完成** | （做了什麼） |
| **驗證** | （工具輸出摘要或證據。若 Build 標籤：先小範圍驗證再全範圍——寫出「小範圍：[範圍] → [結果]；全範圍：[範圍] → [結果]」。範圍太小無法區分時寫「小範圍即全範圍」） |
| **質疑** | 這個產出最容易被挑戰的一點是 ____。判斷：成立（因為 ____）/ 不成立（應改為 ____） |
| **達成目的？** | ✅ 完成 / ⚠️ 完成但產出不足 / ❌ 未完成 |
| **交棒** | 下一步要從這步拿到什麼？能交嗎？不夠 → 先 TodoWrite 追加補充步驟再填。都交了就寫交了什麼。沒有交棒需求寫「—」。 |
| **組件審查** | （若 Review 標籤）[組件名]: (a) 解決 ____ (b) 漏洞：____ / 無漏洞。本步不涉及審查判斷寫「—」|
| **一致性** | （若 Creative 標籤）✅ 無矛盾（核對：[檔案名列表]）/ ⚠️ 矛盾：____。thinking 中先寫 `[一致性核對] 核對 [檔案名:行號] 的 [設定項] → 一致/矛盾` |

上面兩行只在對應標籤啟用時出現。無標籤任務的表格只有前五行。

**Creative 逐步核對補充**：不確定新內容是否與設定矛盾 → Read 設定檔，不從記憶推斷。

**達成目的的判定基準**——判的是這個步驟，不是最終任務：
- **✅ 完成**：步驟動作做了，且拿到了預期產出。
- **⚠️ 完成但產出不足**：步驟動作做了，但沒拿到預期產出（搜了沒找到、查了但來源不可用等）。**⚠️ 時交棒欄不能寫「—」**——必須寫出缺什麼、下一步怎麼補。
- **❌ 未完成**：步驟動作本身失敗（工具錯誤、前置條件不滿足、邏輯錯誤）。注意：如果產出不足的原因是前置假設錯誤（例如讀錯檔案、搜錯關鍵字），歸 ❌ 不歸 ⚠️——因為需要修正假設後重做，不是補充產出。

4. 根據結果決定下一步：

**如果 ✅**：
- 額外問題：過程中有沒有看到跟原本目的無關、但值得處理的問題？有 → 用 TodoWrite 追加新 todo。
- 同類掃描：這步處理了 X，有其他同類 X 需要同步處理嗎？有 → 追加 todo。
- 上下游確認：這步的輸出影響了哪些依賴方或後續步驟？需要同步 → 追加 todo。
- Keeper Test（僅在該步驟涉及方案選擇時）：你考慮過的方案中，排第二的是什麼？為什麼選了目前方案而非它？只考慮過一個方案 → 本身就是需要反省的信號。
- 審查三問（若 Build 標籤）：(1) 跟上下游的接口還相容嗎？ (2) 邊界情況：[列表]，每個的處理：____。列表為空 → 寫「無邊界情況（因為 ____）」 (3) 這是正解還是 workaround？workaround → 記錄技術債。
- 用 TodoWrite 標為 completed，進入下一步。

**如果 ⚠️**：
- 交棒欄已強制填寫（不能寫「—」），其中可能已觸發追加補充步驟。
- 完成三個自檢（同 ✅）。
- 用 TodoWrite 標為 completed，進入下一步（或進入剛追加的補充步驟）。
- 如果是最後一個執行步驟（下一步是交付閉環），交棒寫給閉環的 [目標對照]：說明缺什麼、預期判定為部分達成。

**如果 ❌**：
- 不標 completed。
- **若該步驟由 sub-agent 執行** → 先逐項診斷 prompt：「WHAT: ✅有 / ❌缺→補：____」「DONE: ✅有 / ❌缺→補：____」「DON'T: ✅有 / ❌缺→補：____」「WHY: ✅有 / ❌缺→補：____」。有缺 → 補全 prompt 後重新 spawn（不算同一思路的重試）。四項皆 ✅ 但仍失敗 → 繼續下方流程。
- 寫出：「新假設：[這次補救基於什麼不同於已試方案的假設？]」
  - 能寫出 2+ 個本質不同的新假設，且互不依賴、可獨立驗證 → 先檢查文件域隔離：多個假設是否涉及寫入同一文件？是 → 退回串行嘗試（保留失敗歷史傳遞）。否 → spawn 多個 sub-agent 各走一條路，用結果選贏家。
  - 能寫出 1 個新假設 → 追加補救步驟，繼續處理。
  - 無法寫出新假設（只能寫「再試一次」或空白）→ 觸發「六步排查法」。
- **❌ 後 spawn sub-agent 補救時**，prompt 必須帶入失敗歷史：(1) 已嘗試的方案 (2) 每個方案失敗的原因 (3) 禁止重複的方向。三項資訊不能少。

### 第三步：交付閉環（最後一個 todo）

最終輸出必須包含：

**[任務結果]** 一句話：做了什麼。
**[任務目標對照]** 把開工時的 [任務目標] 原文貼出來，逐字對照 [任務結果]。寫出：達成 / 部分達成 / 未達成，以及差距是什麼。如果不是「達成」→ 觸發「六步排查法」區塊流程（見下方），並把「交付閉環」打回 pending。只有 [任務目標對照] 為「達成」時才能完成交付。**例外**：如果六步排查已完成且放棄門檻已通過，[任務目標對照] 可寫「未達成（已窮盡排查）」——這是合法的完成狀態，不再觸發排查迴圈。

若 [任務標籤] 含 **Creative**，在 [任務完成證據] 之前插入：

**[Creative 自檢]** 固定格式：
```
1. 一致性：✅/⚠️ — 核對了 [檔案列表]，結論：____
2. 角色聲音：✅/⚠️ — [哪些角色可/不可區分，依據]
   - 讀者辨識：遮住作者記憶，逐句掃描——每句對話或動作，讀者只靠文本（不靠推理）能判斷是誰嗎？特別檢查：多人場景中「他/她」是否有歧義、連續對話中說話者切換是否清楚。
3. 設定連動：✅/⚠️ — 受影響項目：[列表] → 逐一確認結論
4. 場景自檢：✅/⚠️ — (a) 推進了 ____ (b) 互動 ✅/⚠️ (c) 無趣段落：[有/無，哪段]
```
每項必須有具體內容（核對了什麼、哪些角色、哪些受影響項目），不接受純 ✅ 沒有細節。

**[任務完成證據]** 能驗證任務完成的證據，不是「我認為正確」。（命令輸出、Read-back、覆蓋維度列舉等）
**[產出影響]** 這次產出影響了哪些其他地方？列出 + 逐項確認。
**[額外處理]** 過程中主動發現並處理的問題（沒有就寫「無」）。
**[核心四問回顧]** 對照開工時的核心四問，哪些判斷對了、哪些錯了。
**[過程回顧]** 這次最耗時或最曲折的一步是第 __ 步，原因是 ____。這個原因是一次性的還是類似任務也會遇到？
- 一次性（因為 ____，類似任務不會遇到的理由：____）→ 結束
- 會再遇到 → 應寫進 ____（CLAUDE.md / skill / hook / memory），具體內容：____

**[零知識審視]**（若 Build 或 Review 標籤）一個不知道這次對話做了什麼的人，只看最終產出，最可能誤解的地方是哪裡？如果存在 → 補充說明或修改產出。

寫完以上各項，才能把「交付閉環」標為 completed。

## 六步排查法

**入口自檢**（三項確認後才進入排查）：
(1) 重讀錯誤訊息全文：已讀 ✅ / 未讀 → 先讀
(2) 換過搜尋關鍵字：已換（列出換過的：____）/ 未換 → 先換
(3) 有更簡單的解法嗎？____
三項確認完畢，仍然卡住 → 進入排查。

用 TodoWrite 追加以下 todo items（content 照抄），逐一執行，每步產物寫在步驟摘要表格中：

```
排查-0：逐層追問根因 + 最小範圍複現（固定首步，所有排查都做）
排查-1：列出所有已試方案 + 總結共同模式 + 指出它們共享的核心假設是什麼
排查-2：逐字讀失敗訊息 + 前後 50 行（引用行號）
排查-3：搜尋錯誤訊息原文 / 官方文件（貼結果）
排查-4：驗證前置假設（版本/路徑/權限/依賴，每個用工具確認）
排查-5：反轉核心假設——假設問題不在原本認為的地方（嘗試結果）
排查-6：列出至少 3 個本質不同方案（A 失敗不會讓 B 也失敗），逐一嘗試
```

**排查-0 機械化格式**：thinking block 中寫 `[根因鏈] L1: 直接原因 → L2: 為什麼 → ... → 根因: ____`，步驟摘要表格中寫根因結論 + 複現結果（如適用）。

**排查-0 完成後**，將失敗歸入一種模式（選最接近的，寫在排查-0 的摘要表格中）：
- 🔄 **原地打轉**（反覆改參數不改思路）→ 排查-5 優先
- 🔍 **沒查就猜**（憑記憶不驗證）→ 排查-3、排查-4 優先
- 💩 **表面完成**（做了但品質不夠）→ 排查-2 優先
- 🚪 **放棄傾向**（想說做不到）→ 排查-6 優先
- ❓ **無法分類** → 按預設順序
分類只影響優先順序，不跳過任何步驟——全部都要做。

完成排查-0 到排查-5 之前不向使用者提問。

---

### 放棄門檻

六步排查完成後仍無法解決 → 宣告做不到前的強制門檻：
1. 寫出：「我的結論依賴的核心假設是 _____」
2. 至少反轉一條假設並用工具嘗試（如果排查-5 已反轉過相同假設，引用該結果即可，不重複）
3. 反轉後也不行，才能宣告做不到
- FAIL: 宣告做不到但沒完成以上 3 步。

通過放棄門檻後 → 回到交付閉環，[任務目標對照] 寫「未達成（已窮盡排查）」。這是合法的完成狀態——agent 交付的是排查過程和結論，不是空手而歸。不再觸發六步排查迴圈。
